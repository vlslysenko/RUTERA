## 1. Продукт в двух словах

✅ RUTERA — облачный сервис (SaaS) для небольших транспортных компаний: автопарк, карта, тахографы, водители (HR), фактуры и дебиторка, CMR, топливо, калькулятор поездки, позже биржи грузов. Всё в одном, максимально просто и дёшево.

✅ Название: **RUTERA** (от ruta / route — маршрут, звучит по-европейски). Репозиторий: https://github.com/vlslysenko/RUTERA.

Класс продукта: TMS (Transport Management System) + fleet management для малых перевозчиков.

## 3. Основополагающие принципы (все ✅)

1. **Максимально интуитивный интерфейс.** Главный принцип продукта.
2. **Минимальные текущие расходы.** Готовый продукт для нас как владельцев должен быть «бесплатным»: платим только за хостинг и домен, минимум абонентских платежей сторонним сервисам. Доход = абонементы клиентов.
3. **Код вместо платного AI.** Там, где можно решить кодом, решаем кодом: лучше отточенный механизм на коде, чем оплата AI. AI не противопоказан, но только там, где без него никак (например, распознавание CMR), и с бесплатной альтернативой как основным вариантом.
4. **AI-доступ ко всем функциям как отдельный платный модуль.** Каждая функция приложения доступна через публичный API, а поверх него MCP-сервер, чтобы ИИ (Claude или другой) мог управлять приложением от имени пользователя с его правами и в рамках его фирмы. Но это отдельная ветка продукта, а не основной канал общения фронтенда с бэкендом: интерфейс React работает через собственный внутренний интерфейс. Управление через ИИ (API + MCP) клиенты получают за отдельную плату (решение 27.10.2026, заменяет прежнюю формулировку «API-first»).
5. **Web + мобильный интерфейс.** 💡 Мобильный как PWA (веб-приложение, которое ставится на телефон), без сборов магазинов приложений.
6. **Один код для standalone и cloud.** Как в SMDP: сначала standalone, целевой вариант — облако. Данные разделяются сущностью Firma.
7. **SMDP — источник кода, только для чтения.** Каталоги SMDP никогда не изменяем. Код не переносим 1:1: модифицируем, делаем современнее, оптимизируем.
8. **Руководства для ИИ по ролям.** Для каждой роли есть файл в `docs/ai-roles/` (README + `owner.md`, `dispatcher.md`, `logistician.md`, `accountant.md`, `driver.md`), который объясняет ИИ-оператору этой роли, какие функции и данные ему доступны и каким самым простым способом их получить. Эти руководства — часть платного модуля «Управление через ИИ» (принцип 4) и **сопровождаются вместе с каждым изменением функций**: правка публичного API или MCP без обновления руководств не принимается.

## 4. Функциональные модули

### 4.1 Автопарк

- ✅ Добавление автомобилей и ведение их данных.
- 💡 Поля, нужные другим модулям: Euro-класс, число осей, масса, высота, средний расход (для калькулятора поездки и платных дорог), привязка водителей и топливных карт, прицепы.

### 4.2 Карта и GPS

- ✅ Карта, на которой видно все автомобили.
- ✅ GPS: вероятно Teltonika, но она платная, поэтому пока отложить или сделать бесплатный вариант.
- 💡 Карта: Leaflet + OpenStreetMap (бесплатно; Google Maps платный, не берём).
- 💡 Приём позиций с трекеров: Traccar как готовый бесплатный GPS-сервер (2000+ моделей трекеров) или подключение к аккаунту клиента у провайдера (Wialon, Webfleet и т.п. через их API). Клиент обычно уже платит за трекеры, мы только подключаемся.
- 💡 (новое, не обсуждалось) Пока трекеров нет, последние позиции можно брать из смарт-тахографов: DDD-файлы Gen2 содержат GNSS-позиции.

### 4.3 Тахографы и контроль водителей

- ✅ Данные с тахографов автоматически импортируются в приложение.
- ✅ Встроенный парсер DDD-файлов обязателен.
- ✅ Контроль работы водителей: время вождения и отдыха, нарушения по регламенту (ЕС) 561/2006.
- 💡 Источники DDD: ручная загрузка файлов (карта водителя и память тахографа), позже API удалённой выгрузки (Webfleet, Tachogram, VDO TIS-Web) или удалённая выгрузка через Teltonika.
- 💡 Парсер: свой на Java, на основе открытых парсеров (readesm, tachoparser). Поддержка тахографов Gen1 и Gen2 (smart).
- 💡 Остаток часов водителя из тахографа используется калькулятором поездки (4.8) и карточкой водителя (4.4).

### 4.4 Водители (HR)

- ✅ Карточка водителя: больничные, отпуска, оплаты (зарплата, суточные), рабочие дни, нарушения (из тахографа) и прочее. Всё в одной карточке.
- Рынок: учёт отпусков и больничных водителей не предлагает ни один конкурент, это свободная ниша (см. раздел 10).

### 4.5 Фактуры и дебиторка

- ✅ Видеть все фактуры и балансы по ним: оплачено, не оплачено, просрочено.
- ✅ Автоматическая отправка писем контрагентам, которые не платят, и учёт этой информации (история отправок).
- 💡 MVP = **учёт** фактур: ввод вручную или импорт, статусы оплаты, напоминания должникам по расписанию с историей. Это просто.
- ✅ (27.10.2026) В MVP только **учёт** фактур. **Выставление** из RUTERA и KSeF (в Польше с 2026 года обязательная отправка через государственную систему, бесплатное API, много деталей) — этап 3 на тех же таблицах: фактура сразу с позициями (`invoice_line`), чтобы выставление добавилось без переделки.

### 4.6 CMR

- ✅ Обработка CMR.
- 💡 Загрузка фото или скана (в том числе с телефона водителя), распознавание текста (OCR), привязка к рейсу и фактуре. OCR: бесплатный Tesseract как основной вариант, AI-распознавание как опция (центы за документ, можно включить в абонемент).
- 💡 e-CMR позже: в Польше внедрение планируется в 2026, в ЕС обязательный приём eFTI с 9 июля 2027, полное распространение около 2029. Никто из продуктов для малых перевозчиков e-CMR пока не предлагает.

### 4.7 Топливо и топливные карты

- ✅ Импорт транзакций топливных карт включаем в план, если это не сложно.
- 💡 Водители в международных перевозках заправляются по топливным картам: DKV, UTA (Edenred), E100, Shell Card, AS24, OMV/Routex. Провайдеры дают выгрузки CSV/XML, у некоторых есть API. Каждая заправка сама появляется в RUTERA: машина, литры, цена, станция, страна. Нужен только доступ клиента к своему кабинету.
- 💡 Результат: расход на 100 км по машине и водителю, стоимость рейса, данные для возврата VAT и акциза.
- 💡 Позже: сверка с GPS и датчиком уровня топлива (Teltonika читает бак через CAN) против воровства топлива; ручной ввод с телефона водителя (фото чека + пробег) для заправок без карты.

### 4.8 Калькулятор поездки на карте

- ✅ Идея владельца: на карте отображена машина, которая едет, например, на выгрузку. Вводишь адрес, и с учётом часов водителя или экипажа и специфики машины система рассчитывает стоимость дороги для этого автомобиля, приблизительное время прибытия, все необходимые паузы, дневные и недельные отдыхи и всю информацию по поездке.
- 💡 Маршрут для грузовика: свой сервер маршрутизации (Valhalla или GraphHopper на OpenStreetMap) с учётом высоты, веса, осей и запретов для грузовиков. Бесплатно, нужно только место на сервере.
- 💡 Паузы и отдых: свой движок правил 561/2006 (4,5 ч вождения → 45 мин перерыва, дневной отдых 11/9 ч, недельный отдых, экипаж из двух водителей). Остаток часов водителя берём из тахографа. Чистый код, без AI.
- 💡 Время прибытия = время в пути + все паузы; на карте видно, где и когда остановиться.
- 💡 Стоимость = топливо (расход машины + цены с топливных карт) + зарплата и суточные водителя + платные дороги. Платные дороги самое сложное: бесплатного API нет, поэтому свои таблицы тарифов по странам (класс Euro, оси, масса); платный сервис вроде TollGuru можно подключить позже.
- 💡 Сложность средне-высокая, отдельный модуль на 1–2 месяца, ставить сразу после MVP. У конкурентов в таком виде этого почти нет.

### 4.9 Биржи грузов

- ✅ Возможные интеграции с Trans.eu и другими подобными биржами заказов.
- 💡 Этап 2–3: API есть, но доступ обычно дают по партнёрскому договору.

### 4.10 Упрощение логистики

- ✅ Заявлено как направление развития.
- 💡 Планирование рейсов и оптимизация маршрутов — самое объёмное, начинать с этого не стоит. Калькулятор поездки (4.8) — первый шаг в эту сторону.

### 4.11 Кабинет водителя

- ✅ Отдельный дашборд для водителей, возможно в рамках этого же облачного приложения.
- 💡 Как PWA на телефоне: фото CMR, статусы рейса, свои часы и нарушения, отпуска и больничные, заправки без карты.

### 4.12 Доступ ИИ: API + MCP (отдельный платный модуль)

- ✅ Ко всем функциям приложения ИИ должен иметь доступ через API или MCP.
- ✅ API и MCP — отдельная ветка продукта, а не основной канал общения фронтенда с бэкендом. Управление приложением через ИИ клиенты получают за отдельную плату (решение 27.10.2026; прежний вариант «API-first», при котором React работал бы только через публичный API, отменён).
- 💡 Архитектура: один общий слой сервисов (бизнес-логика, права, фильтр по Firma), над ним два входа. (1) Внутренний интерфейс для React: контроллеры под `/app/...`, сессия + CSRF, формат ответов под нужды экранов. (2) Публичный API `/api/v1` с описанием OpenAPI и персональными токенами; MCP-сервер (Spring AI MCP) работает поверх публичного API от имени пользователя с его правами. Фронтенд не зависит от публичного API, но публичный API всё равно покрывает все функции, потому что оба входа зовут одни и те же сервисы.
- 💡 Включение модуля: флаг тарифа на уровне Firma («Управление через ИИ»). Без него публичный API и MCP для фирмы закрыты и токены не выдаются. Действия через API/MCP пишутся в аудит с пометкой «через ИИ»; возможны лимиты вызовов по тарифу.
- 💡 Контроль полноты: автоматический тест или отчёт о функциях сервисного слоя, которые не покрыты публичным API, чтобы принцип «все функции доступны ИИ» не разъехался с кодом со временем.
- ✅ (27.10.2026) Авторизация MCP и внешних API-клиентов: персональные API-токены пользователя (в базе только хеш), выдаются только при включённом модуле; права токена = права пользователя.
- ✅ Руководства для ИИ по ролям в `docs/ai-roles/` (принцип 8) входят в этот платный модуль: контекст роли, подключение, таблица доступа, типичные задачи с инструментами, ограничения. Сейчас заготовки версии 0.1, названия инструментов — placeholder до появления API. 💡 MCP-сервер отдаёт руководство роли текущего пользователя как ресурс и стартовую инструкцию; фактическая карта прав пользователя всегда важнее текста руководства.

## 8. Деплой и мультитенантность

- ✅ Как в SMDP: один код и одна схема, приложение может работать как standalone (одна фирма) и как облако (много фирм). Начинаем со standalone, целевой вариант — облако.
- ✅ Сущность Firma (фирма) ограничивает все данные.
- ✅ DevOps, если дойдём: Kubernetes на OVH, возможно AWS (у владельца уже есть конфигурация `ovh-k8st1`).
- ✅ (27.10.2026) Одна БД для всех фирм с `firma_id` в каждой бизнес-таблице и фильтрацией на уровне Hibernate (`@TenantId`); проверка совпадения фирмы в сервисном слое как второй рубеж; единственное исключение — `app_user`, где вход ищет логин до того, как известна фирма. В SMDP фильтрация только ручная, и документ `MULTITENANT_FIRMA_NULL_LEAK.md` описывает утечки, их нужно избежать. Подробности: раздел 16 и `docs/DB_SCHEMA.md`.
- 💡 Миграция standalone → cloud по образцу модуля `utils` SMDP.
- 💡 Standalone = `docker compose`; облако = k8s на OVH, CI/CD через GitHub Actions.

## 9. Переиспользование SMDP

| Логирование | `logback.xml`, `ExdLogger` | как есть |
| Аудит | `Dziennik` | переписать в generic AuditLog + MDC (firmaId, operatorId, requestId) |
| Аутентификация | `SpringWebSecurityConfig`, `SCUserDetailsService`, `DaoAuthenticationProviderExd`, `SmdpPasswordEncoder` (BCrypt), `LoginAttemptService`, `RememberMeService`, TOTP-пакет, `WeakPasswordFilter`, `InviteTokenService`, `SpringHttpSessionConfig` | с доработкой: вырезать RFID/EI/LDAP/Windows/Azure/MD5 |
| Права | `RoleOperator`, механизм `PrivilegesService`, `OwnOpRole`, `checkPriviligesCheck`, фронт-helper | механизм с доработкой, набор ключей переписать под RUTERA; проверку через аннотацию + AOP |
| Email | cloud `SpringEmailConfig`, `EmailService`, Thymeleaf-шаблоны, `EmailNotificationRequest`, отправка после коммита | с доработкой: JMS → async/outbox, без vendor-пула, секрет из env |

| Firma | `Firma`, `Firmazarzadzajaca`, `OperatorContext(HelperService)`, `SystemTypService`, cloud `FirmyFacade` | с доработкой; фильтрацию усилить `@TenantId` |

## 16. База данных: соглашения

Эскиз схемы (8 групп, 56 таблиц, ER-диаграммы): https://claude.ai/artifact/CaWzXPnFBAbA3WozsqBSVg, Markdown `docs/DB_SCHEMA.md`. Соглашения приняты 27.10.2026 (все ✅):

| Тема | Решение |
|---|---|
| Ключи | `id BIGINT AUTO_INCREMENT`, как в SMDP; без UUID. При миграции standalone → cloud идентификаторы перенумеровываются утилитой по образцу модуля `utils` SMDP |
| Арендатор | `firma_id NOT NULL` в каждой бизнес-таблице + Hibernate `@TenantId`; сервисный слой проверяет фирму второй раз; единственное исключение `app_user` |
| Имена | таблицы и колонки по-английски в `snake_case`, единственное число; сущность `firma` сохраняет имя |
| Время | UTC, `DATETIME(6)`; часовой пояс фирмы только для показа |
| Перечисления | строками `VARCHAR`, не порядковыми номерами (урок SMDP) и не типом `ENUM` MySQL |
| Деньги | `DECIMAL(14,2)` + код валюты ISO 4217 на той же строке; базовая валюта фирмы; курсы ЕЦБ в `currency_rate` |
| Удаление | soft delete (`deleted`) только у справочников: машины, водители, контрагенты, пользователи; остальное удаляется физически |
| Общие колонки | `created_at`, `created_by`, `updated_at`, `updated_by`, `version` (оптимистическая блокировка) |
| Индексы | каждый индекс и уникальное ограничение бизнес-таблицы начинаются с `firma_id` |
| Миграции | Flyway, версионные SQL в модуле `common`; `ddl-auto=validate` в тестах и при старте; `mysqldump` перед миграцией в standalone |
| Файлы | одна таблица `stored_file`; DISK в standalone, S3 (OVH) в облаке |
| Почта и задачи | таблица `email_outbox` + Spring Scheduler, ShedLock на MySQL; без брокера |
| i18n | тексты в `messages_xx.properties`, в базе только коды языков |
